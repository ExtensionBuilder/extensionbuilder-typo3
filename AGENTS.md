# AGENTS.md

## Project

This repository contains the TYPO3 extension:

```text
extensionbuilder_typo3
```

Vendor:

```text
ExtensionBuilder
```

PHP namespace:

```text
ExtensionBuilder\ExtensionBuilderTypo3
```

`extensionbuilder_typo3` is an administration tool and editor for TYPO3 extensions.

The extension manages projects, vendors, extensions, and their configurations.
The actual TYPO3 extension code is **not generated directly by `extensionbuilder_typo3`**.

Code generation is performed by a **separate generator extension**.

The basic workflow is:

1. `extensionbuilder_typo3` manages and edits project, vendor, extension, and configuration data.
2. This data is passed to the separate generator extension.
3. The generator extension generates the TYPO3 extension code.
4. The generated code is then returned to the TYPO3 editor or to `extensionbuilder_typo3`.
5. The generated code can be displayed, reviewed, and further edited there.

`extensionbuilder_typo3` processes, among other things:

* Projects
* Vendors
* Extensions
* Components
* Properties
* Models
* Controllers
* Backend modules
* TCA
* Fluid
* XLF
* Content Security Policies
* Generator configurations
* Persistent project JSON data
* Extension code generated by the generator
* Passing generated code to the TYPO3 editor

## Architecture

The basic architecture is:

```text
extensionbuilder_typo3
        ↓
Project and configuration data
        ↓
separate generator extension
        ↓
generated TYPO3 extension code
        ↓
TYPO3 editor / extensionbuilder_typo3
```

Important:

`extensionbuilder_typo3` does not generate TYPO3 extension code itself.

Therefore, when investigating errors, always distinguish between:

1. Source code of `extensionbuilder_typo3`
2. Project, vendor, extension, and configuration data
3. Passing data to the generator extension
4. Source code of the generator extension
5. Generator templates of the generator extension
6. Generated TYPO3 extension code
7. Return of the generated code
8. Display and editing of the code in the TYPO3 editor

Primary target:

```text
TYPO3 14.x
```

Additionally:

* Keep TYPO3 13 compatibility where reasonably possible
* Consider TYPO3 15 for new APIs
* Do not introduce already deprecated TYPO3 APIs
* Prefer future-proof implementations for new code

Primary PHP version:

```text
PHP 8.5
```

Only PHP language features and PHP functions compatible with the supported TYPO3 version may be used.

## General Rules

* Follow the official TYPO3 Coding Guidelines.
* Prefer TYPO3 Core APIs.
* Do not invent TYPO3 APIs.
* Do not invent Fluid ViewHelpers.
* Do not invent classes, methods, partials, routes, or configuration keys.
* Before making changes, always verify that the target actually exists.
* Keep changes as small and local as possible.
* Do not perform unrequested refactorings.
* Do not remove existing functionality.
* Do not rename existing public classes, actions, routes, or configuration keys without explicit instruction.
* Preserve existing behavior wherever possible.
* Do not make purely cosmetic changes to unrelated files.
* Do not completely reformat files when this is not required for the actual change.
* Do not disable security mechanisms as a quick workaround for an error.
* Before every change, check whether a similar implementation already exists in the project.

## ExtensionBuilder-Specific Error Analysis

When an error occurs in generated TYPO3 extension code:

1. Check whether the data in `extensionbuilder_typo3` is stored correctly.
2. Check which data is passed to the generator extension.
3. Check whether the transfer is complete and correct.
4. Check whether the generator extension processes the data correctly.
5. Check whether the error is located in a generator template.
6. Check whether the generated code is already incorrect before it is returned.
7. Check whether the code is modified during the return process.
8. Check whether the TYPO3 editor displays the code correctly.
9. Only then modify the actually responsible extension or file.

If the error is located in the generator extension, it must not be fixed only in the generated code or in the TYPO3 editor.

If the error is located in `extensionbuilder_typo3`, the generator extension must not be changed unnecessarily.

Direct modifications to generated code are generally for analysis only if that code is regenerated during the next generation process.

## Persistent Data Structures

Project, vendor, and extension data may be stored long-term.

Existing keys must not be changed without a backward-compatibility check:

* renamed
* removed
* moved
* changed in data type
* changed in nesting structure

Historical keys such as:

```text
propertys
contentSecurityPolicys
extensionNameLagecy
extensionNameLegacy
```

are especially important.

Even if their spelling is incorrect or inconsistent, these keys must not be silently corrected.

Before changing data structures, check:

* Existing project files
* JSON structures
* Import
* Export
* Build process
* Generator transfer
* Configuration access
* Fluid output
* Stored extensions
* Generator input

## PHP

New PHP files should preferably use:

```php
declare(strict_types=1);
```

Follow TYPO3 and PSR coding standards.

Use typed properties.

Prefer:

```php
private SomeService $someService;
```

Use constructor property promotion when appropriate:

```php
public function __construct(
    private readonly SomeService $someService,
) {
}
```

Prefer dependency injection.

Avoid unnecessarily using:

```php
GeneralUtility::makeInstance(SomeService::class);
```

when constructor injection is possible.

`GeneralUtility::makeInstance()` is permitted when required by TYPO3 architecture or the runtime context.

## PHP Namespaces

Namespaces must follow the TYPO3/PSR structure.

The general namespace for this extension is:

```text
ExtensionBuilder\ExtensionBuilderTypo3
```

Before adding a `use` statement, verify that the class actually exists.

Do not invent classes based on an assumed namespace path.

## Extbase Controllers

Controller actions should return PSR-7 responses.

Example:

```php
public function listAction(): ResponseInterface
{
    return $this->htmlResponse();
}
```

Use:

```php
use Psr\Http\Message\ResponseInterface;
```

Do not use `void` controller actions when TYPO3 expects a response.

Prefer Extbase argument mapping.

Controller arguments and Fluid link arguments must match.

If an action expects:

```php
public function editAction(Extension $extension): ResponseInterface
```

the calling link or redirect must also pass `extension`.

For errors such as:

```text
Required argument "..." is not set
```

always check:

* `f:link.action`
* `f:form`
* Redirects
* Action signature
* Property mapping
* URL parameters
* Controller
* Action names

## ModuleTemplate

Prefer:

* ModuleTemplate
* ModuleTemplateFactory
* PageRenderer
* ButtonBar
* Breadcrumbs
* TYPO3 Backend Routing
* TYPO3 Icon API

Do not unnecessarily recreate backend HTML manually when TYPO3 already provides a suitable API.

## Fluid

Fluid must be compatible with TYPO3 14.

Templates may use the following standard namespaces:

```html
<html
    xmlns:f="http://typo3.org/ns/TYPO3/CMS/Fluid/ViewHelpers"
    xmlns:be="http://typo3.org/ns/TYPO3/CMS/Backend/ViewHelpers"
    xmlns:core="http://typo3.org/ns/TYPO3/CMS/Core/ViewHelpers"
    data-namespace-typo3-fluid="true"
>
```

Important:

`be:` belongs to:

```text
TYPO3/CMS/Backend/ViewHelpers
```

not:

```text
TYPO3/CMS/Core/ViewHelpers
```

Partials do not require an additional `<html>` namespace wrapper.

Layouts may contain namespaces if corresponding ViewHelpers are used there.

## Fluid Expressions

Use direct variables.

Prefer:

```html
arguments="{0: extensionName}"
```

Do not unnecessarily use:

```html
arguments="{0: '{extensionName}'}"
```

For action links, pass arguments directly:

```html
arguments="{
    extension: extension,
    currentProject: currentProject
}"
```

Do not unnecessarily wrap variables as strings.

## Fluid Partials

Before every use, verify that the partial actually exists.

Example:

```html
<f:render partial="ComponentAdd" arguments="{_all}" />
```

requires:

```text
Resources/Private/Partials/ComponentAdd.html
```

Pay exact attention to singular and plural names.

For example:

```text
ComponentAdd.html
```

is not:

```text
ComponentsAdd.html
```

Do not assume missing partials exist.

## Fluid `arguments="{_all}"`

Use `arguments="{_all}"` only when the partial actually requires all variables.

For reusable partials, prefer:

```html
<f:render
    partial="ProjectList"
    arguments="{
        projectData: projectData,
        configuration: configuration
    }"
/>
```

Explicit arguments make dependencies easier to understand.

Do not completely replace existing `{_all}` usage without a reason.

## Fluid Debugging

Temporarily allowed:

```html
<f:debug>{variable}</f:debug>
```

or:

```html
<f:debug inline="1">{variable}</f:debug>
```

Do not leave large `{_all}` dumps permanently in templates.

Remove debug output after the analysis is complete unless it is explicitly required permanently.

## PHP Debugging

Temporarily allowed:

```php
debug($variable);
```

Remove debug output after the analysis is complete.

Do not dump sensitive data:

* Passwords
* Tokens
* API keys
* Secrets
* Session data
* Credentials

## Extbase Variable Dump

If the TYPO3 Extbase variable dump appears unformatted or without its usual presentation, check the Content Security Policy first.

Especially important:

```php
SourceKeyword::nonceProxy
```

for styles.

## Content Security Policy

The extension must work with TYPO3 Content Security Policy enabled.

Never disable CSP globally as a quick fix.

Do not use `unsafe-inline` as the standard solution.

Consider TYPO3 nonce support.

For TYPO3-generated inline scripts and inline styles:

```php
SourceKeyword::nonceProxy
```

should be used when required.

Especially check:

```php
Directive::ScriptSrc
Directive::ScriptSrcElem
Directive::StyleSrc
Directive::StyleSrcElem
```

Example:

```php
new Mutation(
    MutationMode::Set,
    Directive::StyleSrc,
    SourceKeyword::self,
    SourceKeyword::nonceProxy,
),
```

and:

```php
new Mutation(
    MutationMode::Set,
    Directive::StyleSrcElem,
    SourceKeyword::self,
    SourceKeyword::nonceProxy,
),
```

Do not recreate TYPO3 debugger CSS as a workaround before checking CSP and nonce configuration.

## JavaScript

Use modern ES modules.

No inline scripts.

Do not use inline event handlers:

```html
onclick=""
onchange=""
onkeyup=""
```

Instead, use `data-*` attributes and event listeners.

Example:

```html
<button type="button" data-action="delete">
    Delete
</button>
```

JavaScript:

```javascript
document.addEventListener('click', (event) => {
    const target = event.target.closest('[data-action="delete"]');

    if (!target) {
        return;
    }

    // Action
});
```

Use the TYPO3 JavaScript Module API when JavaScript is loaded in the backend.

## PageRenderer

Prefer loading JavaScript and CSS through TYPO3.

For example, Fluid can use:

```html
<f:be.pageRenderer
    includeJavaScriptModules="{0: '@extensionbuilder/extensionbuildertypo3/ExtensionInfo.js'}"
/>
```

Do not unnecessarily include external assets directly with `<script>`.

## CSS

Prefer placing CSS under:

```text
Resources/Public/Css/
```

Avoid inline styles where possible:

```html
style="..."
```

Instead:

```html
class="eb-example"
```

and:

```css
.eb-example {
    ...
}
```

Extension CSS should preferably be scoped to a dedicated container.

Example:

```css
#extensionbuilder-module .eb-component {
    ...
}
```

Avoid global selectors:

```css
* {}
a {}
button {}
table {}
td {}
th {}
```

if they could affect TYPO3 backend components.

Be particularly careful with:

```css
word-break
overflow-wrap
white-space
display
position
overflow
```

Global changes can affect TYPO3 Core components and debug output.

## Icons

Use the TYPO3 Icon API.

Fluid:

```html
<core:icon identifier="actions-open" size="small" />
```

Typical identifiers:

```text
actions-open
actions-delete
actions-add
actions-refresh
```

Before using an unknown icon identifier, verify that it actually exists in TYPO3.

Do not unnecessarily copy TYPO3 Core SVGs.

## Action Buttons

For multiple actions, preferably use:

```html
<div class="btn-group btn-group-sm" role="group">
```

Edit and delete buttons should be inside the same button group when they are intended to be displayed together.

Example:

```html
<td class="text-end">
    <div class="btn-group btn-group-sm" role="group">
        ...
    </div>
</td>
```

Action icons must be properly vertically aligned.

## Tables

Keep tables logically consistent.

The number of logical columns in:

```html
<thead>
```

and:

```html
<tbody>
```

must match.

Do not add empty `<th>` columns merely for visual spacing when there is no corresponding data cell below.

For example, action columns should use:

```html
<th scope="col" class="text-end">
    Action
</th>
```

and:

```html
<td class="text-end">
    ...
</td>
```

Edit/delete actions must be positioned below the action heading.

## Before Every Change

Before making changes:

1. Open the target file.
2. Review the relevant class or function completely.
3. Search for callers.
4. Search for related Fluid files.
5. Check for similar implementations in the project.
6. Consider the TYPO3 version.
7. Check whether data is passed to the generator extension.
8. Check whether the change affects persistent data.

## Troubleshooting

When fixing errors, do not only treat symptoms.

Procedure:

1. Identify a reproducible context.
2. Determine the actual cause.
3. Check the data flow.
4. Check the transfer to the generator extension.
5. Check the generated code.
6. Check the editor return process.
7. Implement the smallest possible change.
8. Check adjacent areas.
9. Check backward compatibility.

## Output for Code Reviews

If the user explicitly requests the complete file, output the complete file.
